## Decisions made

- Operator confirmed `cdawgva` has public R2.dev access and that every future edition will also live there, so repointed `NEXT_PUBLIC_R2_BASE_URL` in place rather than adding a second env var. Verified live against the real bucket before writing any code (`cyclethon-5/donations-full.json` returns 20,998 donations).
- Added an explicit `eventKey` field to `Edition` (`'cyclethon-1'` through `'cyclethon-5'`), matching the pipeline repo's canonical keys, rather than deriving it from `editionNumber`.

- `/2026/donations/live` stays, as a static replay of the frozen data (operator's call) — threaded a new `sourceUrl` prop into `DonationLiveFeed` so its internal 5-minute poll also hits the archived URL instead of the now-404ing unprefixed one; left its SSE connection to `/api/donations/stream` alone since that's the app's own infra, not pipeline data.

## What I learned

The unprefixed `DONATIONS_URL`/`DONATIONS_FULL_URL`/`DONATIONS_STATS_URL` constants (no event prefix) 404 against the new bucket — confirmed by curl before relying on anything. Two call sites used them directly outside the `getDonations*`/`getStats`/`getCampaignFact` wrappers: `DonationsContext`'s default `sourceUrl` (unused here since every 2026 layout already passes an explicit one) and `DonationLiveFeed`'s hardcoded poll, which did need fixing.

## Problems / friction

Non-fatal, data still loads correctly (verified 20,998 donations render), but worth knowing this is a pre-existing Next.js data-cache ceiling, not something this change introduced.

## What I worked on

Created a `/commit` skill (`.claude/skills/commit/SKILL.md`, adapted from the sibling `cdawgva-cyclethon` repo's version) at the operator's request. Operator then asked for a public-repo sensitivity audit of the whole repo, which came back clean, and asked me to harden the skill accordingly. Operator deployed Phase 1 to Vercel (main branch, GitHub-integrated auto-deploy) and found the live site's donation data missing — root-caused to four client-side hooks Phase 1's sweep had missed, fixed those, operator redeployed.

## Decisions made

- Narrowed this repo's `.gitignore` from blanket `.claude/` to `.claude/settings.local.json` only, matching the sibling repo, so skills get tracked and shared via git instead of staying local-only. Confirmed `settings.local.json` itself (just a Bash permission allowlist, no secrets) stays correctly excluded after the change.
- Hardened the `/commit` skill in two passes: added a mechanical secret-pattern grep as a deterministic backstop to the manual diff read, then broadened the manual-read step's framing from "Tiltify donor data" specifically to the general principle (any real person's personal details, not just credential-shaped secrets or donor data) per operator's explicit clarification.
- Root cause of the missing-data bug: Phase 1's sweep only searched for callers of the four server-side `getDonations`/`getDonationsFull`/`getStats`/`getCampaignFact` wrapper functions. It missed `useActivityBuckets.ts`, `useDailyTotals.ts`, `useCampaignFactPoll.ts` (unused dead code, fixed anyway), and `useDayDonations.ts` — four client-side hooks that fetched the unprefixed R2 constants directly in their own `useEffect`, bypassing all of Phase 1's plumbing entirely. Fixed each by reading the current edition via the existing `useEditionContext()` (the pattern this codebase already uses for exactly this "which year am I" problem, per 2026-09-13's journal) rather than prop-drilling a URL through each component tree.
- Added `getArchivedDonationsDayUrl(eventKey, dateStr)` to `constants.ts` since no per-day-snapshot URL helper existed yet.
- After confirming the fix live, removed the now-fully-dead unprefixed `DONATIONS_URL`/`DONATIONS_FULL_URL`/`DONATIONS_STATS_URL` constants and their use as default parameter values across `getDonations`/`getDonationsFull`/`getStats`/`getCampaignFact`/`DonationsContext`'s `sourceUrl`/`DonationLiveFeed`'s `sourceUrl`, making `url`/`sourceUrl` required everywhere instead. These defaults pointed at URLs that 404 against the real bucket and were a silent-failure landmine for any future caller that forgot to pass an explicit archived URL; `npm run check`/`build` passing clean after the change confirmed every real caller was already explicit.

## What I learned

A repo-wide security audit (full git history, not just the working tree) found nothing: no `.env*` file was ever committed, no API-key/token/AWS-key/private-key patterns anywhere in history, no hardcoded donor PII in scripts/fixtures/docs ever, now or previously. The one hit worth checking (`docs/donations-stats-schema.md`'s example aggregate totals) turned out to be fine since it's the same kind of aggregate data the live site already shows publicly.

The browser automation tool's sandbox can't reach this machine's `localhost` (confirmed: curl succeeds, the extension's own `navigate`/`screenshot` calls fail with "showing error page" regardless of `localhost` vs `127.0.0.1`). It works fine against real public URLs though, which is what let me verify the live Vercel deploy's actual network requests and a real screenshot once the fix was redeployed.

## Problems / friction

None significant. The missing-hooks bug was a real gap in Phase 1's verification (I'd checked build/typecheck and a handful of page loads, but hadn't grepped broadly enough for every direct `fetch()` of the raw R2 constants) — worth remembering for similar "repoint every data call" tasks going forward: search for the raw constant/base-URL symbol being replaced, not just the higher-level wrapper functions built on top of it.
