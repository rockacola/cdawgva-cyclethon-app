# 2026-09-13

## What I worked on

Operator flagged that Header/Footer nav still routed through the unprefixed redirects (`/journey` instead of `/2026/journey`) while browsing `/2026/...`, and that Header/Footer are conceptually year-specific chrome, not shared app-wide chrome. Moved them into a `/2026/layout.tsx` that instantiates them with `year={2026}` baked in.

## Decisions made

- Removed `Header`/`Footer` from the root layout entirely rather than keeping a "default" instance there. There's currently no page that renders body content directly under the root — everything real lives under a year's own layout, or is a redirect that never renders a body — so a root-level instance would have been dead code.
- `Header`/`Footer` take an optional `year` prop (default `CURRENT_EDITION.year`) instead of sniffing `usePathname()`. Removed `getEditionFromPath` from `editions.ts` since nothing needs it anymore.
- Kept `Header`/`Footer` as one shared, parameterized component rather than literally forking them per year — there's nothing yet for a year's nav to diverge in shape from. Refork only when a year's nav structure actually needs to differ, consistent with how page content is already handled.
- `/about-cyclethon` and `/about` nav hrefs point at their current real location (`/2026/about-cyclethon`, `/2026/about`) rather than a hypothetical future unprefixed one — operator mentioned these will likely become year-agnostic pages later, but that hasn't happened yet, so linking to where the content isn't yet would just add a redirect hop today for no benefit.

The Header/Footer fix doesn't cover in-page content links written directly into components — there are likely more of these; fix opportunistically when found rather than as a dedicated sweep.

## What I worked on

Operator's actual report ("the /journey page sidebar links don't have /2026 prefix") pointed at `DayNav`, not Header/Footer directly. Fixed that, and rather than keep prop-drilling `year` through every component that needed it (Header/Footer already did this earlier today), introduced `EditionProvider`/`useEditionContext()` and switched everything over to it, since the pattern was clearly going to keep recurring.

## Decisions made

- Added `src/providers/EditionProvider.tsx` (matching the existing `Locale`/`Timezone`/`Appearance` provider convention) rather than continuing to pass an explicit `year` prop to each component. `/2026/layout.tsx` now wraps its children in `<EditionProvider year={2026}>`; `Header`, `Footer`, and `DayNav` all switched from a `year` prop to `useEditionContext()`.
- While fixing `DayNav`, proactively grepped the rest of `src/components` for the same hardcoded-unprefixed-link pattern rather than waiting for the operator to find each one individually. Found and fixed two more: `LatestDonations`'s "view all donations" link and `JourneyPageContent`'s finish-line link. Both switched to `useEditionContext()` too.

## What I learned

The `year` prop approach from earlier today (Header/Footer) was a reasonable first fix but didn't scale — every new component that needed the year would have required threading the prop through one more layer, or duplicating the "which year am I" logic. A context scoped to each year's own layout was the better fit from the start; worth remembering for next time this kind of "which X am I under" question comes up.
