# 2026-11-13

## What I worked on

Investigated a Vercel email reporting 100% usage of the free team's ISR Writes quota (200,000). Traced it to this app's 2026 pages and lib fetchers still using hourly time-based revalidation (`revalidate = 3600`, `FETCH_CACHE_REVALIDATE = 3600`) for data that can never change: every edition in `editions.ts`/the pipeline repo's `campaign.ts` is archived (`isLive: false`), so the hourly re-fetch/re-cache cycle was pure waste as long as the pages got any traffic.

## Decisions made

- Switched all time-based revalidation to indefinite caching instead of raising the interval: `export const revalidate = false` on `2026/page.tsx`, `2026/donations/layout.tsx`, `2026/donations/live/page.tsx`, `2026/stats/layout.tsx`, and `next: { revalidate: false }` in `getDonations`, `getDonationsFull`, `getStats`, `getCampaignFact`. Removed the now-unused `FETCH_CACHE_REVALIDATE` constant.
- Chose `false` over simply deleting the option, since an explicit `false` signals the archived-data assumption is deliberate rather than leaving a reader to wonder whether revalidation was forgotten.

## What I learned

The team-level ISR Writes quota in the Vercel email is shared across every project on the Hobby/Pro team, not scoped to this project alone, so this fix addresses a real source of waste but isn't confirmed as the sole cause without checking the Vercel dashboard's per-project breakdown.

## Problems / friction

None. `npm run check` passed clean after the change.

## Next step

Watch the Vercel usage dashboard after this deploys to confirm ISR Writes drop; if the team is still near the quota, check other projects under the same team for similarly short revalidate windows.
